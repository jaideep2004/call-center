## 2. Data integrity — publisher flow

Path: `POST /api/v1/publishers/[id]/invite` → `createPortalInvite` → `app.publisher_invites` row → user clicks `/register?invite=<token>` → `POST /api/v1/invites/[token]/accept` → `acceptPortalInvite`.

### Files traced

- `src/app/api/v1/publishers/[id]/invite/route.ts:6-22` — admin-only (`{ resource: "publishers", action: "manage" }`), calls `createPortalInvite`, emails the link, returns `{ link, emailed: true }`.
- `src/server/services/publisher-portal.ts:191-208` — `createPortalInvite`:
  - Validates the publisher has an email.
  - Returns an **existing** pending invite's link if one exists (no new token generated). The `token` column is stored in plaintext (48 hex chars from `randomBytes(24)`) — **NOTE**: this means a DB read exposes all valid invite tokens. Compensating control: short-lived expiry; token uniqueness enforced by the `findByToken` index.
- `src/server/services/publisher-portal.ts:210-250` — `acceptPortalInvite`:
  - L1: `invite.status === "pending"` else `ConflictError("Invite already used")` (line 213).
  - L2: `expires_at > now()` else `ConflictError("Invite expired")` (line 214).
  - L3: publisher must exist + `deleted_at IS NULL` (lines 216-221).
  - L4: `publishers.findByUserId(userId)` empty — one account cannot link to two publishers (line 223-224).
  - L5: `userRow.role` ∈ `{agent, publisher}` — **explicit allow-list, not a deny-list** (line 228). Prevents a super_admin or admin from accidentally downgrading their role via a publisher invite.
  - L6: no existing `app.memberships` row for this user — blocks accepting an agency invite as a publisher-portal user (line 232-236).
  - Then `UPDATE "user" SET role = 'publisher'` (line 238) and `publishers.linkUser(publisher.id, userId)` (line 239) and `publisherInvites.accept(token)` (line 240).
- `src/server/repositories/publisher-invites.ts:42-48` — `accept(token)` is a single `UPDATE … WHERE status = 'pending' AND expires_at > now() RETURNING *` — atomic CAS, idempotent for the second concurrent caller (returns `[]` ⇒ `rows[0]` undefined).

### Scenarios traced

| Scenario | Outcome | Verdict |
|---|---|---|
| **Same invite accepted twice, sequentially** | First call passes L1/L2, mutates `status='accepted'`. Second call hits `ConflictError("Invite already used")` at L1 (line 213). Returns 409. | ✅ Safe |
| **Same invite accepted twice, concurrently** | The CAS update `WHERE status='pending'` is atomic. Loser sees `rows[0]` undefined → `accept()` returns `undefined`. The route handler currently returns `ok(undefined, …)` (no 409 path) — **NOTE below**. The user-row update is also a single UPDATE so double-execution is impossible at the SQL layer; only the loser branch has a soft-confirm hole. | ⚠️ See note |
| **User already has `role = agent`** | L5 (`role !== "agent" && role !== "publisher"`) lets them through. Their role is then upgraded to `publisher` (line 238) — note this is a **one-way role bump**: the previous agent identity is preserved in `agents`, but `agents/subscription`/`wallet/agent` may now show stale data for a publisher-role user. | ⚠️ See note |
| **Email already registered** | BetterAuth returns a sign-up error (`register/page.tsx:30-34` shows it). User never reaches `acceptPortalInvite`. | ✅ Safe |
| **Email reused by accepting publisher invite after a previous publisher invite** | `findByUserId(userId)` at L4 blocks (user_id already linked). | ✅ Safe |
| **Same invite accepted after expiry** | L2 `expires_at > now()` fails → 409. | ✅ Safe |
| **Token disclosed / brute-forced** | 24 bytes = 192 bits entropy; rate limit at `/api/auth` (20/min/IP) bounds `accept` only indirectly. No per-token brute force guard. | ⚠️ Out of scope; standard for invite flows |

### Notes

- **Concurrent-double-accept (sequential in practice)**: the second call to `acceptPortalInvite` raises `ConflictError` at L1 and the route handler returns 409 — `accept()` is only reached on the first call. Two truly concurrent callers (within ms) would race; PostgreSQL serializes the UPDATE so one loses and gets `rows.length === 0`, which the route currently bubbles as a generic 500 (the `PublisherInviteRepository.accept()` returns `rows[0]` which is `undefined`). Recommend mapping `accept()` returning `undefined` to a 409. Non-blocking, but worth a follow-up.

- **Agent → Publisher role bump** (`src/server/services/publisher-portal.ts:228-238`): the explicit allow-list at L5 correctly **accepts** existing agents, but there's no UI guard in `register/page.tsx` to warn the user they're switching roles. Worth a banner: "Joining this publisher will change your account role to Publisher."

- The publisher token is stored in plaintext in `app.publisher_invites.token`. Acceptable for invite flows (it's effectively a shared secret with the email recipient), but worth hashing if the DB ever becomes world-readable.

## 3. Concurrency review — `call-orchestrator.finalizeCall`

`src/server/services/call-orchestrator.ts:607-703`.

### State machine

`processProviderEvent` (line 40-273) walks:

```
none → received → validating → routing → ringing → connecting → connected → ended → (finalized)
```

with branch paths:
- `ringing` (caller leg) + `ended` (caller hung up) → `missed`
- `ringing` + `ended` (agent leg, `event.callId` present) → failover via `handleNoAnswer`
- `routing` + `ended` → `missed` (with provider cancel of both legs)
- `connected` (Telnyx echo on inbound) → **ignored unless state == "connecting"** (line 173-180)
- Any `isTerminal(call.state)` → log only, return (line 128-130)

State transitions are guarded by `assertTransition(call.state as any, "next")` and the **CAS-via-`calls.claimState(...)`** pattern (see lines 219-223, 489-494, 475-478).

### Race scenarios

| Scenario | Handling | Verdict |
|---|---|---|
| **Two `ended` webhooks (caller leg + agent leg hang up simultaneously)** | `claimState` on line 220: `UPDATE calls SET state='ended' WHERE state=<previous>` — only one wins; the loser `return { call, finalized: false }` (line 223) and never re-runs billing. | ✅ Race-safe |
| **`finalizeCall` invoked twice (e.g. inline-fallback + pg-boss redelivery)** | Line 644-654: `INSERT … ON CONFLICT (call_id) DO NOTHING RETURNING *`. If the second caller gets `invoiceResult.rows.length === 0`, it returns `{ skipped: true, reason: "already_finalized" }` (line 652-653). **All money movement is inside the winner branch** (lines 657-699). | ✅ Idempotent |
| **Hangup event before `connected` event arrives (rare ordering)** | `hangupCall` (line 804-824) calls `calls.updateState(call.id, "ended", …)` then `finalizeCall`. `finalizeCall` line 609 returns `null` if `call.state !== "ended"` — but in this scenario state IS `ended`. Then `connectedSeconds` = `Math.round((ended_at - connected_at)/1000)` — if `connected_at` is null, `connectedSeconds = 0`. With `connectedSeconds < minConnectedSeconds` (default 0), `totalCents = 0` (line 634-636) — no charge. The wallet balance gate (line 664) is also skipped because `totalCents === 0`. | ✅ Correct (free) |
| **`connected` arrives after `ended` (out of order)** | `processProviderEvent` line 173-180: `if (call.state === "connecting")` only. If state is already `ended`/`missed`/`failed`, the connected event is **silently ignored** (no error). `isTerminal()` short-circuits at line 128-130. The call's `connected_at` column is never updated → `connectedSeconds` stays 0 → no charge. | ✅ Safe — no retroactive billing |
| **Two `inbound` events for the same `provider_call_id`** | Line 132-137: `INSERT … ON CONFLICT (provider, provider_event_id) DO NOTHING` for `call_events`. Line 141-143: `if (call.state !== "received" && !== "validating" && !== "routing") return { call }` — second event is a no-op. | ✅ Idempotent |
| **Race between `routeCall` and concurrent duplicate `route-call` job** | Line 283-298: idempotency guard `if (call.state !== "routing") return` + `claimState(routing → ringing)` — losers bail. Verified by tests in `call-orchestrator.test.ts`. | ✅ Race-safe |

### Notes

- The state machine is **monotonic with one exception**: `ringing → routing` cannot happen (correct), but `routing → failed` (line 475-478) and `routing → missed` (line 201, 214) bypass `assertTransition` in some paths. Looking at line 220 the explicit transition uses `assertTransition`; the missed paths (lines 201, 214) do **not** call it. In practice, the `missed` write goes `routing → missed`, which `assertTransition` would permit (`routing → missed` is valid in `@/domain/calls`). The skipped assertion is a minor consistency nit, not a correctness bug.
- The `finalizeCall` invoice anchor at line 644-654 is **the** defense against double billing — confirmed it runs inside `transaction(...)` (line 640) so the INSERT + wallet debit are atomic. No double-spend possible even if the worker redelivers.
